**Requirements:** RC-05, RC-04, §11 · **Date:** 2026-09-28 · **Model:** `jev-1.13.0` (every response)
**Command:** `dotnet run --project Cognition/src/Cognition.Eval -- jev-billing --live --max-cost-usd 0.10 --repeats 20 --tiny-repeats 3`
**Fixture:** `Cognition/fixtures/jev/billing/` — a decision state rendered from the `decision.yaml` template

**Raw data (gitignored):** `docs/reports/raw/T1.03b/` (`calls.csv`, `summary.json`, one JSON per exchange).
**Spent:** 92 calls, 312,418 input tokens, **$0.0131**. 0 errors, 0 retries.

## Result: billed per call, not per question

The state is billed **once per call**, whatever the number of questions. Question text (instructions and
criteria) is billed on top, once per question.

Method: every question set was sent twice, over the full state and over a one-line state
(`tiny_state`, 55 chars). The difference is what the state itself costs.

| Questions | Input tokens, full state | Input tokens, tiny state | State cost (difference) | If billed per question |
|---:|---:|---:|---:|---:|
| 1 | 2,871 | 451 | **2,420** | 2,420 |
| 5 | 3,464 | 1,044 | **2,420** | 12,100 |
| 10 | 4,073 | 1,653 | **2,420** | 24,200 |
| 13 (full decision) | 4,438 | 2,018 | **2,420** | 31,460 |

Token counts were identical on all 20 repeats of each set (min = median = max). Output tokens grow with
questions (78 → 781) but are free. This matches the official docs ("Jev ingests the `state` once and
evaluates every question against it", `/models`; 12.2x cheaper batched in `/cookbooks/parallel_questions`).

**Per RC-05 this keeps full fan-out: `[decision] fanout = "full"` stays as is.** Also, per the note in
`memory_filter.yaml`, the memory filter may batch several events into one call.

Other numbers from this run:
- Each extra question adds about **130 tokens** on average (1 → 13 questions: +1,567 tokens for 12
  questions), so the questions are 45% of a full 13-question decision call.
- There is a fixed overhead per call of a few hundred tokens: a one-line state with one question already
  bills 451 tokens.
- The real tokenizer gave 4.43 chars/token on this English state; `chars_per_token_initial = 4.0` is
  conservative (it overestimates by ~10%). T1.14 recalibrates it.

## Revised §11 estimate (Jev only) — for owner approval

Assumptions as in §11: 15 characters, 0.5 decisions/s each → **27,000 decisions/hour**; $0.042 per
million input tokens. Question cost measured above (~2,020 tokens for the full 13, ~1,040 for 5).

| Case | Tokens per decision | Jev $/hour |
|---|---:|---:|
| §11 original assumption | 3,800 | $4.31 |
| Full fan-out (13), state as in this fixture (2,420) | 4,438 | **$5.03** |
| Full fan-out (13), state at the `context.target_tokens` target (4,000) | ~6,020 | **$6.82** |
| Reduced (action + ~4 sub-menus), state 2,420 | ~3,460 | $3.93 |
| Reduced (action + ~4 sub-menus), state 4,000 | ~5,040 | $5.72 |
| Full fan-out, state 2,420, cadence 0.35 Hz | 4,438 | $3.52 |

**What this means for RC-04 (≤ $6/h total with 15 characters):** billing is per call, so fan-out itself is
cheap. But question text is billed on every call, and the §11 figure left no room for it. With a 4k-token
state, Jev alone would pass $6/h before any LLM cost (speech, summaries, deep thought). With the ~2.4k
state of this fixture it costs about $5/h, which leaves ~$1/h for the LLMs.

The levers, in order of impact: state size (T1.14), decision cadence (T1.17, E-03), question and option text
length (the prompts), fan-out (per-call billing makes this the weakest lever).

**Recommended default (pending owner decision, see `docs/questions.md` Q-1):** keep `fanout = "full"`; aim
the decision state at ~2.5k tokens in T1.14 (the "2.5k context target" already listed in the phase-1 risk
table) while keeping `hard_cap_tokens` as is; measure real cadence and LLM cost in T1.31 and only then
decide whether to reduce fan-out or cadence.
